# Agentless Advanced TopN

Supported Advanced Agentless charts try the new ranking by default on the system monitoring store. The ordinary Console metrics write alias (for example, `.infini_metrics`, with the configured ORM prefix) is used for the query, rather than the legacy search wildcard. Advanced Agentless manual selection uses the same raw bucket and point rules for supported index and node charts. It queries authorized exact index names or explicit node transport addresses, and displays available curves in request order without ranking. Legacy node selectors without `node_selector=transport_address`, other pages, and `doc_percent` are unchanged. Node counter searches try one bounded search and may fall back to PIT within the same deadline.

Node and index charts prefer one strict PIT snapshot when the store supports it (Easysearch, Elasticsearch 8.16+, and OpenSearch 2.4+): two searches for peaks or pagination for counters. If the snapshot cannot open, the same request falls back to one bounded single search. Older or unsupported versions always use the bounded single search. The bounded search carries a sentinel that proves the candidate set is too large to rank completely; a partial result is never ranked. These attempts share the same deadline. If neither can produce a complete result, supported automatic charts explain the failure instead of showing the legacy activity ranking.

TopN ranks the available valid monitoring samples within the requested bounds. Missing observations are not zero; a missing predecessor omits the difference, and gaps can break lines. No usable points after a complete search produces an empty chart. Failed, partial or truncated searches never produce an empty or partial ranking.

The optional `insight.topn.raw_index` overrides the trusted original index or alias (not a wildcard or rollup). Only explicit `cluster_id` matches are accepted; UUID-only samples are not included.

The first batch covers 17 index and 27 node single-field peaks. The second covers 20 index and 43 node derived metrics: rates, operation latencies, same-bucket ratios and positive store-size change. The node count describes backend keys; the Advanced page exposes a version-dependent subset. Document percentage (`doc_percent`) is not a TopN chart and stays on the existing path.

All paths score and draw from the same validated points. Zero is valid when measured; a missing field or a latency without requests is not a zero. Ratios require both fields from the same observation and a positive denominator (total bytes for disk). A parameterized Painless aggregation returns the maximum valid ratio per bucket, including dense buckets. Latency differences use paired counters from one observation per bucket, ordered by operation count and then timestamp. These exact queries require inline Painless support on the monitoring store; failures do not fall back to sampling. The previous complete bucket may be read to evaluate the first visible difference; its samples do not rank. Missing or non-adjacent buckets, index UUID/node ID changes, detectable topology changes and counter resets are not scored. Node counter differences assume no JVM restart inside the requested window: a restart resets counters, and the affected transition is skipped by the counter-reset check rather than scored across lifetimes. First-release ranking therefore verifies identity, adjacency, topology and counter monotonicity, but not process lifetime. The Framework keeps the JVM start estimate (`jvm.timestamp - jvm.uptime_in millis` as `start_time_estimate_in_millis`) on the `keep/jvm-start-estimate` branch for a later lifetime check. Storage decreases are skipped but remain the baseline for the next bucket. GC time keeps its legacy per-second formula and units. This is a ranking of retained valid monitoring samples, not proof that collection or counter continuity was perfect.

When the monitoring store rewrites a search onto rollup data (an `origin` stamp on the response), the chart is drawn from that approximation instead of failing: the rewritten search's shard layout is not compared, ratio and peak aggregations read the rolled values, counter differences keep their bucket pairing, and latency pairs that a rollup cannot provide fall back to the difference of the per-field maxima (bounded by the same monotonicity and operation-count guards). Raw pages keep the strict diagnostics, so a missing paired observation on a raw store still fails the chart rather than silently dropping points.

Queries are limited to 512 visible time buckets, four concurrent exact requests per Console process, up to 32 storage shards per PIT, and a five-second query deadline (or a shorter requested timeout); automatic scans spanning more than a day use the wait budget instead (30 seconds by default). Composite scans also stop at 48 search pages (including a possible terminal probe) or 150,000 entity-time buckets. The page size is reduced for wider windows. PIT deletion has an independent two-second deadline; short PIT expiry is the fallback if the latest ID is not available. These are protections, not production performance guarantees. Budget or deadline rejection discards any partial ranking and suggests a shorter window, a larger interval, or manual selection. Long windows use the same bounded raw path. A complete empty result still renders as an empty chart. Agent, unsupported or legacy manual requests, and `doc_percent` retain their existing paths.

The opt-in snapshot integration test requires a disposable Easysearch instance at `127.0.0.1:19219` named `console-topn-local-bench`; run `CONSOLE_TOPN_INTEGRATION=1 go test ./modules/elastic/api/internal/topn -count=1`. Test fixtures use a newly named temporary index and do not target existing monitoring data.

Elasticsearch 6.8–7.1 uses `interval` for fixed-second date buckets; Elasticsearch 7.2 and newer use `fixed_interval`. The 6.8 compatibility integration test runs against a disposable Elasticsearch instance named `console-topn-local-bench` on `127.0.0.1:19220`: `CONSOLE_TOPN_ES68_INTEGRATION=1 go test ./modules/elastic/api/internal/topn -run TestElasticsearch68SingleSearch -count=1`.
