# Agentless Advanced TopN

Supported Advanced Agentless charts try the new ranking by default on the system monitoring store. The ordinary Console metrics write alias (for example, `.infini_metrics`, with the configured ORM prefix) is used for the query, not the legacy search wildcard that can also match summary indices. Advanced Agentless manual selection uses the same raw bucket and point rules for supported index and node charts. It queries authorized exact index names or explicit node transport addresses, and displays available curves in request order without ranking or reading materialized scores. Legacy node selectors without `node_selector=transport_address`, other pages, and `doc_percent` are unchanged. Node counter searches may retry with mixed JVM evidence within the same budget; ratios retain the per-bucket sample limit.

Node charts try one bounded search first. If its sentinel proves the candidate set is too large and PIT succeeds, Console remembers that route for 30 seconds (up to 128 entries per process). Matching requests skip the single search, including sliding windows with the same duration and bucket count. Hints are scoped to the store, cluster, index, metric and window shape; they do not cache rankings. If a hinted PIT cannot open, the request drops the hint and tries the bounded single search within the remaining deadline. Index charts prefer PIT (two searches for peaks or pagination for counters) when strict PIT is available: Easysearch, Elasticsearch 8.16+, and OpenSearch 2.4+. Older or unsupported versions try one bounded search without PIT. A sentinel detects truncated candidate sets; a partial result is never ranked. Node charts can try PIT after an unsuccessful bounded scan; index charts can try the bounded search when PIT cannot be opened. These attempts share the same deadline. If neither can produce a complete result, supported automatic charts explain the failure instead of showing the legacy activity ranking.

TopN ranks the available valid monitoring samples within the requested bounds. Missing observations are not zero; a missing predecessor omits the difference, and gaps can break lines. No usable points after a complete search produces an empty chart. Failed, partial or truncated searches never produce an empty or partial ranking.

The optional `insight.topn.raw_index` overrides the trusted original index or alias (not a wildcard or rollup). The old `raw_from` setting is no longer used. Only explicit `cluster_id` matches are accepted; UUID-only samples are not included.

The first batch covers 17 index and 27 node single-field peaks. The second covers 20 index and 43 node derived metrics: rates, operation latencies, same-bucket ratios and positive store-size change. The node count describes backend keys; the Advanced page exposes a version-dependent subset. Document percentage (`doc_percent`) is not a TopN chart and stays on the existing path.

All paths score and draw from the same validated points. Zero is valid when measured; a missing field or a latency without requests is not a zero. Ratios require both fields from the same observation and a positive denominator (total bytes for disk); the chart uses the maximum valid ratio per bucket. At most 100 observations per entity and bucket are read; exceeding that limit rejects the whole ranking, rather than ranking a sample. The previous complete bucket may be read to evaluate the first visible difference; its samples do not rank. Missing or non-adjacent buckets, index UUID/node ID changes, detectable topology changes and counter resets are not scored. For node differences, the Agentless Framework collector stores the estimated JVM start (`jvm.timestamp - jvm.uptime_in_millis`) as `payload.elasticsearch.node_stats.jvm.start_time_estimate_in_millis`. It is an integer millisecond value; raw metrics mappings must allow numeric doc values (the default mappings infer a `long`). In the same search or PIT, if every observation in the query scope has the field, only the minimum, maximum and value count per bucket are returned. The value count must match the bucket's sample count. In mixed windows, the query still uses summaries for new samples; only samples without an estimate require the bounded per-sample lookup (up to 64 such observations per bucket). Missing, truncated or mixed-lifetime buckets break both neighboring differences; estimated starts must agree within one second. No historical backfill is performed. Long-window improvements require that the new collector has populated the entire scan, including any optional preceding bucket used in a difference. Direct gauges are unchanged by JVM evidence handling. Storage decreases are skipped but remain the baseline for the next bucket. GC time keeps its legacy per-second formula and units. This is a ranking of retained valid monitoring samples, not proof that collection or counter continuity was perfect.

The initial limits are deliberately conservative: 512 visible time buckets, four concurrent exact requests per Console process, up to 32 storage shards per PIT, a five-second query deadline (or a shorter requested timeout), and 24 MiB of cumulative decoded response data across the single attempt and PIT requests. Composite scans also stop at 48 search pages (including a possible terminal probe) or 150,000 entity-time buckets. The page size is reduced for wider windows. The decoded response is bounded while reading. PIT deletion has an independent two-second deadline and a small separate response cap; short PIT expiry is the fallback if the latest ID is not available. These are protections, not production performance guarantees. Budget rejection discards any partial ranking and suggests a shorter window, a larger interval, or manual selection. A complete empty result still renders as an empty chart. Agent, unsupported or legacy manual requests, and `doc_percent` retain their existing paths.

## Materialized long-window index counters

Default is off. A single Console instance can enable the on-demand mode with:

```yaml
insight:
  topn:
    materialized:
      enabled: true
```

When the raw write index has a lifecycle policy, the writer creates and validates `.console-topn-index-rate-v2` on the system monitoring store, subject to store permissions. The four supported charts are indexing rate, query rate, indexing latency and query latency. Fully covered requests use the existing summary path. An opted-in browser request with missing summaries queues bounded work for the exact requested window and polls the same endpoint. No proactive historical backfill runs in this mode. A complete result uses available samples, not an assumed full retention window. A completely evaluated transition can save an empty summary only when both raw dependency buckets are verified. Absent raw buckets never produce summary documents. Only full-index authorization can publish newly computed sealed buckets for shared use; partial ACL results stay in the short process-local cache. Known `raw_gaps` suppress affected transitions rather than rejecting the entire window.

Specify `writer: false` on all but one replica. On-demand requests and their polls must reach the writer in multi-instance deployments; other replicas can read existing summaries. Each writer runs at most one on-demand computation at a time; queue and results are process-local and do not survive restart. Hand selection, short windows and other metrics retain their query paths.

Existing explicit `index`, `writer`, `read`, `clusters`, `metrics` and `read_metrics` settings remain supported. Without `enabled`, the original explicit mode still requires a pre-provisioned concrete index (mapping `_meta.console_topn: 1`), and its writer runs the existing scheduled backfill. With `enabled`, explicit `read` and `writer` override their defaults; omitted `metrics` selects all four, omitted `read_metrics` follows `metrics`, and omitted `clusters` does not impose a cluster allowlist. Keep the dedicated index outside the metrics rollup. Use a compatible rollover policy for the summary schema; custom actions such as downsampling raw fields may not apply to summaries. Summaries are a cache of the live original source, not a separate historical tier. Both the predecessor and current bucket must match the original backing index names, UUIDs and observation counts in a raw PIT. A missing raw bucket cannot be published; a changed dependency requires a new summary or a bounded raw recomputation. Previously generated summaries without this provenance are not used. Cached background results are also checked before use. The monitoring account needs permission to read the original index UUID settings. This detects retention and changes in observation counts, not same-count in-place edits. Invalidation follows the raw read view. New single-switch deployments use `.console-topn-index-rate-v2` by default. If the current raw write index is managed, Console provisions a dedicated summary rollover alias and binds the same ILM/ISM policy by name, without changing the raw policy or adding an expiry scheduler. The policy runs on the summary's own rollover clock. OpenSearch's writer tick attaches that policy to unmanaged summary generations without editing its ISM template. If raw has no policy and no summary exists, the browser can still request a bounded calculation; no permanent summary is created. A changed policy binding on a managed summary requires a new summary name; Console does not rebind or delete old indices. Existing concrete summary indices are left in place; to use native rollover, choose a new summary name (or the new default) and let the cache rebuild. The service account requires policy inspection and summary provisioning permissions. Strict PIT support is required.
